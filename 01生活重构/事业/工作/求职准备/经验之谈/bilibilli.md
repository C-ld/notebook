## 那些年，我被坑过的开源项目【让编程再次伟大#19】

https://www.bilibili.com/video/BV1u7mjYpETD/?spm_id_from=333.1007.tianma.1-3-3.click&vd_source=83876cd4a75f8c522c8297ad6b626348

> 不要低估开源软件可能出现的问题。一个项目好坏与否，不完全取决于它的 bug 多不多，或者更新是否频繁。

> semantic versioning 很重要！

> 物联网行业，一万个人一万种硬件和系统配置，动不动就会出现兼容问题

> 如何闭坑开源项目，总的来说就是得把每个开源项目当成一个外包团队，这个团队可能会有不靠谱的开发路线、不靠谱的开发者、不靠谱的 PR 审核、不靠谱的测试覆盖、不靠谱的安全设计；同时，因为你没给他们付钱，所以出了问题也不能找他们背锅。那么如何在降低开发成本的同时减轻风险？就需要调研其背后的团队和管理水平。

> github star 多的，不一定很重要，可能只是业内用的人多

- 开源软件容易出现的问题：
	- 开源软件大多因为是用爱发电，长期维护难以为继，所以可能 3 - 5 年就被遗弃或者停摆了
		- “被弃坑”更深层次的常见原因：它所在的底层技术经常出现 `breaking change`，一旦底层变了，项目就要跟着改所有受影响的代码（很复杂，要考虑兼容问题、改 test case、跟现有逻辑的冲突）。所以底层越不稳，项目越容易被弃坑
		- eg：微信生态圈----Taro，京东的开源小程序框架（含前端），因为更改实在太过频繁撑不住，只好放弃了 UI 任务转移给前端组
	- 很多没有企业在背后控制的、自主形成的开源软件没有明确的发展路线。容易形成“集体管理”的结构，大家都是老好人。一些看起来符合规范，但其实不需要甚至有隐患的 PR 也被合并
		- 树莓派旗下 pi-gen 项目，一个用户提了 QCOW 的系统格式替换现有的打包格式，导致后来出现了很多报错，实际上也并没有给项目带来好处。导致作者不得不自己 fork 一个 pi-gen，自己维护（非常麻烦）。后来 issue 有 1/3 是各种打包格式故障，开发组最后被迫移除 QCOW 所有相关实现。
	- 开源世界到处都是“草台班子”，大的开源组织（Apache基金会、Linux基金会、CNCF等）有成熟的项目管理框架，所以其项目至少四平八稳
		- GraphQL 架构，后端方面选择很多，但前端很少，最主流的框架 apollo-client 来自一个叫 Apollo GraphQL 的公司。其员工未经任何公开讨论就改变了一个实现，并且本地直接合并到 main 分支。后续面对质疑，开发组表示无所谓，不接受回滚、默认关闭新特性、甚至不接受开关、拒绝给出一个向后兼容的方案
- 如何避坑：
	- 相对来说，企业开发的版本生命力会更久（社区版），因为开发者拿钱干活
	- 一个解决办法：别更新，锁定版本
	- 辨别草台班子的小技巧：搜 issue 时采用如下过滤，看对争议最多的问题开发组的处理方法和态度
		- `is:issue sort:comments-desc` 

天下没有白吃的午餐，虽然开源项目可以免费使用，但一旦出了问题，开发者也不会担责。很多项目的管理也不规范或者比较随便。
