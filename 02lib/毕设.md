# levelDB

单线程操作，通过LSM树结构将随机读写转化为顺序读写，从而极大提高写入效率。但是带来了写放大的问题（Compaction中）。

查找：通过64位序列号（最高8位没使用，最低字节存值类型）+键合成lookupKey进行查找

对数据库进行写操作会改变序列号，每写一次序列号+1

## 基本操作
### get
锁，获取参数中序列号（没有则取当前序列号），获取mem、imm、current，并都施加引用，解锁。依次查找mem、imm、sstables，锁，压缩，解除引用。

## 论文整理
### Compation Granularity 压缩粒度
一个与压缩策略的 eagerness 想正交的一个维度。现存的压缩设计都可以在粒度上分为两类：Partial Merge 和 Full Merge，它们各有特定的缺陷。

### Partial Merge 局部归并
每个run（一轮归并产生的数据文件），被分成多个等大的小文件。**LevelDB和RocksDB采用的就是这个策略。**
它的核心问题是**高写放大**。原因有两点：1、被选择合并的文件往往键值对范围并不重叠，因此每次压缩都会额外重写一些不必要的数据。2、同时发生在不同层级的压缩会导致不同生命周期的文件在SSD中分散，这使得SSD硬盘执行垃圾回收的降低，数据规模越大这个问题越明显。

### Full Merge 完全归并
完全合并会把整个级别全部合并。其核心问题是，在合并操作完成之前，无法处理被合并的文件。这意味着压缩LSM-tree的最大级别（它比其他级别大指数级）需要在操作完成之前拥有比用户数据多两倍的存储容量。所以其**存储使用率达不到50%**。

### Space Amplification 空间放大
总空间放大 = 1+转移空间放大+持续空间放大

**临时空间放大：** 多版本并发控制会阻止系统释放一个文件的空间直到它参与的压缩结束。在压缩过程中需要的临时额外空间开销（用于同时存储源数据和合并数据）被称为临时空间放大。
**持续空间放大：** 过时的条目依然在占用空间，直到压缩时被丢弃。

### Write Amplification 写放大
总写放大 = 压缩写放大 x GC（垃圾回收）写放大

总写放大其实是一个数据条目在内存中的总重写次数的平均值。需要降低它来减少对存储带宽和生命周期的开销。除了压缩活动本身带来的重写外，GC活动本身因为会对存在erase unit内的有效数据迁移，所以也会重写数据。

### Merge Policy 归并策略
决定哪些数据参与合并，分为 leveling 和 tiering 两种主流方法。


### Spooky 针对键值对存储的分区压缩方法
1~X-1层采用完全归并，潜入合并（diving merge）到X层，X~L层采用分区合并（partition merge）



# Code Space
主要代码集成在compaction_picker_smart.h/.cc

了解顺序——compaction_picker.h，compaction_picker_smart.h，compaction_picker_smart.cc

compaction_picker抽象类：
- 虚函数
	NeedCompaction()触发压缩行为，PickCompaction()选择要压缩的文件并选定输出位置。
- 非虚函数
	CompactRange() 和 CompactFiles()基于用户的request选择文件进行压缩，内部只有少量关于Compaction style 的逻辑

PickCompaction——选择压缩层级和文件，如果没有压缩要进行返回空指针，否则返回一个堆分配的结构Compaction，该结构描述了压缩相关信息。
```
virtual Compaction* PickCompaction(
      const std::string& cf_name, 
      const MutableCFOptions& mutable_cf_options,
      const MutableDBOptions& mutable_db_options, 
      VersionStorageInfo* vstorage,
      LogBuffer* log_buffer,
      SequenceNumber earliest_memtable_seqno = kMaxSequenceNumber) = 0;
```
